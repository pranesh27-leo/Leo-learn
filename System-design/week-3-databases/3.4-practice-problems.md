## Problem 1: Replication lag

Users complain: after updating profile, friends still see old name for 30 seconds. Stack: master-slave MySQL, reads from slaves.

**Cause?** **Fixes?**

<details>
<summary>Guided solution</summary>

**Async replication lag.** Fixes: read-your-wwrites from master for owner; session stickiness to caught-up replica; reduce lag (faster network, fewer slave load); cache invalidation on write; show “updating…” UX briefly.

</details>

---

## Problem 2: Shard key

1 billion users table. Shard by `last_name_initial` vs `user_id` hash?

<details>
<summary>Guided solution</summary>

**user_id hash** (or consistent hashing)—even spread. Last name skews (**many** “Smith”) → **hot shard**. Joins across shards still hard either way.

</details>

## Problem 3: Store picker

Requirements: **Ticket inventory**, 50k seats, no double sell; peak 10k purchases/minute.

**SQL, Redis, Mongo, Cassandra?** **Combo?**

<details>
<summary>Guided solution</summary>

**SQL** (or strongly consistent KV) for inventory with transactional decrement / optimistic locking. **Redis** optional for hold tokens with TTL during checkout. Not AP-only Cassandra for seat count without careful linearizable design.

</details>

---

## Problem 4: Denormalization

Comment table joins `users` for author display name on every feed load—p95 800ms.

**One schema change?** **Trade-off?**

<details>
<summary>Guided solution</summary>

Add `author_display_name` on `comments`, update on user rename (async or sync). **Trade-off:** duplicate data; must update comments on name change or accept staleness.

</details>

---

## Problem 5: Federation

Monolith DB 2 TB, teams stepping on each other. Propose **federation** split.

<details>
<summary>Guided solution</summary>

Example: `auth_db`, `catalog_db`, `orders_db`, `analytics_db`. App services own their DB. Cross-domain via APIs/events—not SQL joins across DBs.

</details>

---

## Problem 6: Graph vs SQL

“Friends of friends within 3 hops” for 500M users.

**Why graph or alternative?**

<details>
<summary>Guided solution</summary>

Deep joins in SQL explode. Options: **graph DB** for online queries; or **precompute** suggestions offline (batch graph on Hadoop/Spark) stored in KV for reads. Instagram-style hybrid fan-out + offline jobs (Week 6).

</details>
