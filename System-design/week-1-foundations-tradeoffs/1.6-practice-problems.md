## Problem 1: Diagnose performance vs scalability

A note-taking app is fast when 10 people use it. With 10,000 concurrent users at 9 AM, save requests take 30+ seconds.

**Questions:**

1. Is this primarily performance or scalability?
2. Name three architectural changes (not micro-optimizations).

<details>
<summary>Guided solution</summary>

1. **Scalability**—works for low concurrency, fails under load.
2. Examples: horizontal scale stateless API; connection pool + read replicas; queue writes and ack fast; shard documents by user_id; cache frequent reads; rate limit abusive clients.

</details>

## Problem 2: Latency vs throughput

A log aggregation system ingests **1 TB/day**. Product asks: “Can we batch logs every 5 minutes before indexing to save cost?”

**What improves? What might worsen?**

<details>
<summary>Guided solution</summary>

**Throughput / cost** improves—batch compress and bulk-index fewer operations.

**Latency** to search new logs worsens—up to 5 minutes before logs appear in search. Acceptable for security audit; unacceptable for realtime fraud alerts. Offer **two paths**: hot stream (low latency) vs cold batch (high throughput).

</details>

## Problem 3: CAP choice

Design a **hotel room booking** system (100 rooms, no double-booking allowed).

During a network partition between two data centers, should you favor CP or AP? Why?

<details>
<summary>Guided solution</summary>

**CP** (or strong consistency on inventory): better to **reject booking** or show “try again” than confirm two guests for same room. Use single authoritative inventory partition, quorum writes, or lease-based locking. AP with merge is risky for finite inventory unless you have **oversbooking math** (airlines)—hotels usually don’t.

</details>

## Problem 4: Consistency pattern

Match feature to **weak / eventual / strong**:

1. Chat message order in a single room  
2. Global DNS update for new server IP  
3. VoIP audio during 2-second disconnect  

<details>
<summary>Guided solution</summary>

1. **Strong** (or strong per room channel)—users expect ordered messages in one thread; often single partition or sequence numbers.
2. **Eventual**—DNS TTL propagation worldwide.
3. **Weak**—lost audio not replayed; realtime over perfect history.

</details>

## Problem 5: Availability math

Service A and B each **99.9%** available. Request must call **both in sequence**.

What is approximate end-to-end availability?

<details>
<summary>Guided solution</summary>

0.999 × 0.999 = **0.998001 ≈ 99.8%**—worse than either alone. Mitigation: reduce serial dependencies, cache A/B responses, timeouts with graceful degradation, parallelize where possible.

</details>

## Problem 6: Design snippet — status page

**99.95%** SLA for API. One region, single DB, no replica.

**What fails first in an AZ outage?** One improvement for **availability** without full multi-region.

<details>
<summary>Guided solution</summary>

**Fails:** entire API if AZ down—DB SPOF too. **Improvement:** Multi-AZ deployment (LB + app in 2 AZs), RDS Multi-AZ or primary + hot standby, automated failover, health checks. Still single-region risk—document RTO/RPO for region disaster separately.

</details>
