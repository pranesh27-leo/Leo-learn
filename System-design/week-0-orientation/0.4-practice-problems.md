## Problem 1: Clarifying requirements

**Prompt:** “Design Dropbox file sync.”

**Your task:** List **10 clarifying questions** you would ask the interviewer.

<details>
<summary>Guided solution (click to expand)</summary>

Sample questions:

1. Personal only or teams/enterprise sharing?
2. Max file size? Total storage per user?
3. Sync conflict resolution—last-write-wins or versioning?
4. Mobile + desktop + web—all platforms?
5. Offline edits and later sync?
6. Expected users and files per user?
7. Read-heavy (download) vs write-heavy (upload)?
8. Encryption at rest/in transit requirements?
9. Global users—multi-region latency targets?
10. Dedupe identical files across users (content-addressed storage)?

**Why it matters:** Dropbox’s core is **chunked files**, **metadata DB**, **blob storage**, **sync notifications**—scope decides whether you mention **delta sync** and **conflict handling**.

</details>

## Problem 2: High-level boxes

**Prompt:** “Design a rate limiter for a public API.”

**Your task:** Draw (on paper) a high-level diagram with **at most 6 labeled components** and one sentence per arrow.

<details>
<summary>Guided solution</summary>

Example components:

1. **API client**
2. **API gateway / edge** (first enforcement point)
3. **Rate limit service** (token bucket / sliding window)
4. **Redis** (central counter store, fast increments)
5. **Backend API** (only reached if under limit)
6. Optional: **config service** (limits per API key tier)

Flow: Client → Gateway → check Redis counters → allow/deny → Backend.

**Real-world:** Stripe and Cloudflare document rate limits at the edge to protect origin servers.

</details>

## Problem 3: QPS math

**Given:**

- 20 million DAU
- Each user views **40 feed items per day** (each view = 1 read API call)
- Each user creates **2 posts per day** (2 write API calls)

**Tasks:**

1. Compute average read QPS and write QPS.
2. If peak traffic is **5×** average, what is peak read QPS?
3. Is this system read-heavy or write-heavy?

<details>
<summary>Guided solution</summary>

Reads/day = 20M × 40 = **800M/day**  
Writes/day = 20M × 2 = **40M/day**

Read QPS_avg = 800M / 86400 ≈ **9,260/s**  
Write QPS_avg = 40M / 86400 ≈ **463/s**

Peak read ≈ 5 × 9260 ≈ **46,300/s** (round **~50k**)

Read:write ratio ≈ 40:1 → **read-heavy** → cache feed fragments, read replicas, CDN for media; async pipeline for fan-out on writes.

</details>

## Problem 4: Storage math

**Given:** Video platform stores **720p** renditions; average **500 MB per hour-long video**. **100,000** new uploads per day. Metadata **2 KB** per video in SQL.

**Tasks:**

1. Storage added per day for video blobs.
2. Metadata storage per day (negligible or not?).
3. Storage after 1 year (ignore compression/deletion).

<details>
<summary>Guided solution</summary>

1. Blob/day = 100k × 500 MB = **50,000,000 MB/day** ≈ **50 PB/day** — wait, 100k × 500MB = 50e6 MB = 50e3 GB = **50 TB/day** (500 MB × 100k = 50,000,000 MB = 50 TB).

2. Metadata/day = 100k × 2 KB = **200 MB/day** — negligible vs video.

3. One year ≈ 50 TB × 365 ≈ **18 PB** — object storage (S3/GCS), lifecycle to cold tier; not one PostgreSQL cluster for blobs.

</details>

## Problem 5: Mini design (full four steps)

**Prompt:** Design **Bit.ly-style** URL shortening for **internal company links only** (10k employees, not public internet).

**Constraints given:**

- ~1k new links/day
- ~100k redirects/day
- Links expire after 1 year

Walk through Steps 1–4 in writing (half page each).

<details>
<summary>Guided solution sketch</summary>

**Step 1:** Internal auth (SSO); create/list links; redirect; expiry job; no custom domains.

**Step 2:** Browser → corporate LB → monolith or small service → PostgreSQL + optional Redis cache.

**Step 3:**

- `POST /links { url }` → generate 6-char code, store `(code, url, expires_at)`
- `GET /{code}` → 302 redirect
- Cron deletes expired rows

**Step 4:** At this scale, **single DB + Redis cache** is enough; no sharding. Mention backup and SSO anyway.

Contrast with Week 6 public Pastebin at **100M+** links/month.

</details>

## Problem 6: Latency reasoning

**Why** would a social feed feel slow if you fetch, for each of 500 friends, their latest post from a separate database query (N+1 pattern)?

<details>
<summary>Guided solution</summary>

500 sequential DB round trips × ~1–5 ms each → **0.5–2.5+ seconds** minimum, plus app overhead. Fix: **precomputed feed** (fan-out on write or fan-out on read with caching), **single query** with `IN (...)` batching, or **timeline cache** in Redis. Real-world: Twitter/X hybrid fan-out models (Week 6).

</details>
