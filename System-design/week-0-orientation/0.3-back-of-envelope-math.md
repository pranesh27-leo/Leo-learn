# Back-of-the-Envelope Math

## What is it, in one line?

**Quick estimates** of traffic, storage, and hardware needs using round numbers—so your design matches reality.

---

## Why it exists

Interviewers and architects ask: “How much storage?” “How many servers?” You cannot know exactly, but **order-of-magnitude** answers show you think about scale.

Wrong by 2× is fine. Wrong by 1000× means the design falls apart.

---

## Powers of two (memorize these)

Computers count in binary. Capacity and RAM are often powers of two.

| Power | Exact value | Approximation |
|-------|-------------|---------------|
| 2^10 | 1,024 | ~1 thousand (**1 KB** in many contexts) |
| 2^20 | 1,048,576 | ~1 million (**1 MB**) |
| 2^30 | 1,073,741,824 | ~1 billion bytes (**1 GB**) |
| 2^40 | | ~1 trillion bytes (**1 TB**) |
| 2^50 | | ~1 quadrillion bytes (**1 PB**) |

**Rule of thumb:** 2^10 ≈ 10^3, 2^20 ≈ 10^6, 2^30 ≈ 10^9.

## Latency numbers every programmer should know

These are **ballpark** orders of magnitude (hardware and networks change, but ratios matter).

| Operation | Rough time |
|-----------|------------|
| L1 cache reference | ~1 ns |
| Branch mispredict | ~3 ns |
| L2 cache | ~10 ns |
| Mutex lock/unlock | ~100 ns |
| Main memory reference | ~100 ns |
| Compress 1 KB | ~3 μs |
| Send 2 KB over 1 Gbps network | ~20 μs |
| Read 1 MB sequentially from memory | ~10 μs |
| SSD random read | ~100 μs |
| Read 1 MB sequentially from SSD | ~1 ms |
| Round trip same datacenter | ~0.5 ms |
| Read 1 MB from network | ~10 ms |
| Disk seek | ~10 ms |
| Round trip CA ↔ Netherlands | ~150 ms |

**Lesson:** Memory is **orders of magnitude** faster than disk. Network between continents is **slow**—hence **CDNs** and **regional deployment**.

**Real-world:** Netflix places content in edge caches so “read 1 MB from network” is often “read from nearby POP,” not cross-country every time.

## QPS (queries per second) from daily usage

Formula:

```
QPS_average = (requests_per_day) / 86,400
QPS_peak ≈ QPS_average × 2 to 10  (often use ×3 for interviews)
```

**Example:** 100M users, each generates **20 API calls/day** on average.

- Requests/day = 100M × 20 = **2B/day**
- Average QPS = 2B / 86400 ≈ **23,000 QPS**
- Peak ≈ 3 × 23k ≈ **70,000 QPS** (round to **100k** for headroom)

If **read:write = 100:1**:

- Writes ≈ 100k / 101 ≈ **1k write QPS**
- Reads ≈ **99k read QPS**

That tells you: **cache and read replicas** matter more than write sharding (unless writes are heavy per request).

## Storage estimate

**Example: URL shortener**

Assumptions:

- 500M new URLs per year
- Row: short_code (7 B) + long_url (avg 100 B) + metadata (50 B) ≈ **200 B** per row (round up)

Storage/year ≈ 500M × 200 B = **100 GB/year** (order of magnitude)

10-year retention → **~1 TB** (plus indexes overhead → plan **2–3 TB**)

**Example: Photo app**

- 50M DAU, 10% upload 1 photo/day
- 5M uploads/day × 2 MB average = **10 TB/day** raw

You immediately know: object storage (S3), not a SQL BLOB column for originals; metadata in DB.

---

## Bandwidth

```
Bandwidth = QPS × average_response_size
```

**Example:** 99k read QPS × 1 KB response ≈ **99 GB/s** at peak—unrealistic on one host; need CDN, caching, and many servers. Catching impossible numbers early is the point.

## Servers (very rough)

If one modest app server handles **~1k–5k** simple HTTP QPS (highly variable):

- 100k QPS → **20–100** app instances (plus LB, autoscaling)

Always say: “Depends on work per request; I’d load test, but for the interview I assume …”

## Availability quick reference (“nines”)

| Availability | Downtime per year (approx.) |
|--------------|----------------------------|
| 99% (two 9s) | 3.65 days |
| 99.9% (three 9s) | 8.76 hours |
| 99.99% (four 9s) | 52.6 minutes |
| 99.999% (five 9s) | 5.26 minutes |

**Combined systems:** If two **independent** services in **series** each have 99.9% availability:

```
Total ≈ 0.999 × 0.999 = 0.998 = 99.8%
```

**Parallel redundancy** improves availability (see Week 1 availability patterns).

## Worked mini-problem: Chat messages

**Given:**

- 10M DAU
- Each sends 50 messages/day
- Message size avg 200 bytes stored

**Messages/day:** 10M × 50 = **500M/day**

**Write QPS (messages):** 500M / 86400 ≈ **5.8k/s**

**Storage/day:** 500M × 200 B = **100 GB/day**

**Implications:**

- Need append-friendly storage (NoSQL, partitioned logs, or sharded SQL).
- Hot recent chats in cache; old in cheaper storage.
- Async fan-out for push notifications.

## Interview phrases that sound professional

- “Let me assume X and Y; we can adjust if product says otherwise.”
- “That’s read-heavy, so I’ll optimize the read path first.”
- “At this storage growth, we shard by `user_id` within two years.”
- “Cross-region latency dominates; we’ll use a CDN / regional reads.”

---

## Recap

- Use **powers of two** and **latency hierarchy** (CPU → RAM → SSD → network).
- Convert **DAU × actions/day** → **QPS**; apply **read/write split**.
- Estimate **storage** per record × volume × retention.
- Sanity-check **bandwidth** and server count.
