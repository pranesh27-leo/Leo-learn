# Week 4 — Practice Problems

---

## Problem 1: Cache-aside bug

After order placed, “my orders” list still empty until TTL (5 min). Code updates `orders` table but not cache.

**Fix?**

<details>
<summary>Guided solution</summary>

On write: **delete** `orders:user:{id}` cache key or update cached list. Prefer delete for simplicity. Shorter TTL as backup only.

</details>

---

## Problem 2: Write-through vs write-behind

Analytics **page view** counter, 500k/s, losing few counts OK for dashboard.

**Strategy?**

<details>
<summary>Guided solution</summary>

**Write-behind** or in-memory aggregate + periodic batch flush to DB/time-series store. Not write-through to SQL row per view. Use Redis INCR + flush job.

</details>

---

## Problem 3: Queue choice

Need **replay** of all order events for new fraud model training; 50k orders/min.

**Redis list vs Kafka?**

<details>
<summary>Guided solution</summary>

**Kafka** (or similar log)—durable retention, consumer groups, replay. Redis as primary log risky for long retention at scale.

</details>

---

## Problem 4: Back pressure

Queue depth growing 10k/min; p99 API latency rising.

**Two actions?**

<details>
<summary>Guided solution</summary>

1. **Scale consumers** (more workers) if CPU-bound processing.  
2. **Back pressure** at API—429/503 when queue > threshold; shed load.  
3. Fix slow consumer; dead-letter queue for poison messages.

</details>

---

## Problem 5: Thundering herd

Celebrity posts; cache key `feed:celebrity_id` expires; DB melts.

**Mitigations?**

<details>
<summary>Guided solution</summary>

**Single-flight** lock on rebuild; **refresh-ahead** for known hot keys; local L1 cache on app; random TTL jitter; pre-warm cache on post publish via queue.

</details>
