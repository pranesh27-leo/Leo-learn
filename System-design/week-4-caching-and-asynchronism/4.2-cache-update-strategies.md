# Cache Update Strategies

## What is it, in one line?

**Cache update strategies** define who writes the cache and when—on read miss, on every write, async behind, or proactive refresh.

---

## Why it exists

Wrong strategy → stale data, slow writes, or lost updates on cache crash.

---

## Cache-aside (lazy loading)

**Flow (Primer):**

1. App reads cache
2. **Miss** → read DB → write cache → return
3. On DB update, app **updates or deletes** cache entry

**Pros:** Only cache what’s requested; simple.  
**Cons:** Miss = 3 trips; stale until TTL or invalidation; cold empty node after failure.

**Real-world:** Most web apps with Memcached/Redis.

```python
# Pattern (conceptual)
user = cache.get(f"user:{id}")
if user is None:
    user = db.get_user(id)
    cache.set(f"user:{id}", user, ttl=3600)
return user
```

---

## Write-through

App writes **cache first**; cache **synchronously** writes DB.

**Pros:** Cache always fresh for reads after write.  
**Cons:** Slower writes; cache may store data never read.

Combine with cache-aside on read for cold nodes.

---

## Write-behind (write-back)

App writes cache; cache **async** flushes to DB.

**Pros:** Fast writes, batch DB updates.  
**Cons:** **Data loss** if cache dies before flush; harder to implement.

**Real-world:** Some high-write counters where brief loss acceptable with reconciliation—not for money.

---

## Refresh-ahead

Proactively refresh popular keys **before TTL expires** if access pattern predictable.

**Pros:** Lower tail latency on hot keys.  
**Cons:** Wrong prediction wastes work.

---

## TTL as safety net

Even with invalidation, set **TTL** so stale data eventually dies.

**Jitter** TTL to prevent simultaneous expiry (thundering herd).

---

## Comparison table

| Strategy | Read after write | Write speed | Complexity | Loss risk |
|----------|------------------|-------------|------------|-----------|
| Cache-aside | If invalidate OK | Fast | Low | Low |
| Write-through | Fresh | Slower | Medium | Low |
| Write-behind | Fresh in cache | Fastest | High | Medium |
| Refresh-ahead | Fresh hot keys | N/A | Medium | Low |

---

## Interview questions

- “Update user profile—cache strategy?” — Cache-aside: write DB, **delete** cache key (or update); TTL backup.
- “Counter increments 100k/s?” — Redis INCR; periodic flush to DB or write-behind with risk acceptance.

---

## Recap

- **Cache-aside** default for reads; invalidate on write.
- **Write-through** when read-after-write consistency matters.
- **Write-behind** for extreme write rate with eyes open on durability.
