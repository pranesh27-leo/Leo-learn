# HTTP (Hypertext Transfer Protocol)

## What is it, in one line?

**HTTP** is the application-layer **request/response** protocol browsers and APIs use—methods, URLs, headers, and status codes.

---

## Why it exists

Clients and servers need a **standard** way to fetch pages, submit forms, and call APIs over the network. HTTP rides on **TCP** (usually TLS as HTTPS).

---

## Common methods (Primer)

| Method | Use | Idempotent | Safe |
|--------|-----|------------|------|
| GET | Read resource | Yes | Yes |
| POST | Create / action | No | No |
| PUT | Replace resource | Yes | No |
| PATCH | Partial update | No | No |
| DELETE | Remove | Yes | No |

**Idempotent:** repeat call → same effect (e.g. DELETE twice—resource still gone).

**Safe:** GET should not change server state.

---

## Request/response shape

```
GET /api/v1/users/42 HTTP/1.1
Host: api.example.com
Authorization: Bearer ...
Accept: application/json
```

```
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: max-age=60

{"id":42,"name":"Ada"}
```

**Status codes:** 2xx success, 4xx client error, 5xx server error—use standard codes in REST APIs.

---

## HTTP in system design

- **Stateless** servers scale horizontally (session in cookie + server-side store).
- **Cache-Control** enables client and CDN caching.
- **HTTPS everywhere** — TLS at LB or server.
- **HTTP/2** multiplexing; **HTTP/3** over QUIC for lossy networks.

**Real-world:** GitHub REST API—resources as URLs, JSON bodies, rate limit headers.

---

## Interview tips

- Prefer **GET** for reads; don’t change state with GET.
- **POST** for create when server assigns id; **PUT** to known URL.
- Version APIs: `/v1/` path or Accept header.

---

## Recap

- HTTP = verbs + URLs + headers + status.
