## Problem 1: HTTP method

“Transfer money” exposed as `GET /transfer?from=1&to=2&amount=100`.

**What's wrong?**

<details>
<summary>Guided solution</summary>

GET must be **safe** (no state change). Transfers are **side effects** → **POST** (or PUT with idempotency key). Also sensitive data in URL logs. Use POST + auth + idempotency.

</details>

---

## Problem 2: TCP vs UDP

Live multiplayer racing game—position updates 60/s, old positions useless.

**Protocol?** **Why?**

<details>
<summary>Guided solution</summary>

**UDP** — latest position matters; lost packet replaced by next frame. TCP retransmit would increase latency. App may interpolate missing states.

</details>

## Problem 3: REST vs RPC

Internal 40-service mesh; mobile app needs one public API.

**Sketch architecture.**

<details>
<summary>Guided solution</summary>

**gRPC** (or similar) service-to-service; **API Gateway** exposes **REST/JSON** (or GraphQL BFF) to mobile. Gateway handles auth, rate limit, aggregation.

</details>

---

## Problem 4: Security design

Public API stores user medical notes.

**List 5 controls.**

<details>
<summary>Guided solution</summary>

HTTPS; encrypt at rest; strong auth (MFA); authz per record; audit logs; minimal retention; no secrets in client; WAF; parameterized DB queries; private network for DB; compliance (HIPAA) BAA with cloud vendor.

</details>

---

## Problem 5: OOD — LRU Cache

Capacity 2. Sequence: put(1,a), put(2,b), get(1), put(3,c).

**Which key evicted?** **Why?**

<details>
<summary>Guided solution</summary>

Evict **2**. After get(1), order MRU: 1,2. put(3) evicts LRU **2**.

</details>
